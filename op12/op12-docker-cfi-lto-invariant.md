Hard-won rules for building a **Docker/cgroup-enabled** OnePlus 12 kernel that actually boots. BASELINE BOOTS BUT BREAKS NETWORKING (2026-09-15): the clean from-source stock kernel (0-CRC, honest vermagic, NO bypass; boot-op12-stockA-ge02429a7e0f3.img, kernel sha d3d169ef…) flashed to boot_a and BOOTED to Android (display/surfaceflinger fine, 463 modules Live incl. cnss2/wlan_firmware_service), BUT WiFi will NOT enable (no wlan0; runtime init/firmware-handshake failure, not a module reject) and cellular has SIM but NO DATA (no IP on rmnet, "network unreachable"). So booting + modules-loading is necessary but NOT sufficient — runtime radio bringup (QMI/QRTR/remoteproc firmware load) fails. NOTE: initial "cellular up" report was wrong (SIM-detected ≠ data-working); do not trust presence-of-interface as proof. ROOT CAUSE FOUND + verified in dmesg (baseline_dmesg.txt, sha 12c759b2…): the device has TWO GKI module sets — Google-signed **system_dlkm** at `6.1.57-android14-11-o-g26041213ac6c` AND OnePlus **vendor_dlkm** at `-g41519d41cdba` (DIFFERENT GKI sub-versions). Our clean build set `CONFIG_MODULE_SIG_PROTECT=y` + `MODULE_SIG_KEY="certs/signing_key.pem"` (from-source key) → system_dlkm modules (Google-signed) rejected with "Permission denied" (EACCES); rfkill.ko fails → WiFi/BT radio disabled → no wlan0; modem rproc down → no data. vendor_dlkm loaded fine (not sig-protected) — hence "modules Live" but networking dead. THE LESSON: a clean no-bypass from-source kernel CANNOT work on this device — you MUST (1) disable MODULE_SIG_PROTECT (+ don't force our sig) so Google-signed system_dlkm loads, and (2) bypass check_version/same_magic so BOTH GKI sub-versions load despite our single vermagic. This VINDICATES the original force-load approach: the bypass is MANDATORY for baseline function, NOT Docker-specific. "0-CRC vs vendor bar + booted + modules Live" is necessary but NOT sufficient (system_dlkm was never in that bar). Ruled OUT by full .config diff vs WildKernel (extracted from GOLDEN via scripts/extract-ikconfig → vendor-ref/wildkernel.config): NO missing CNSS/MHI/PCI/QMI/QRTR/IPA/remoteproc/modem config — our build is a superset; WildKernel-only configs are just KSU/SUSFS, BBG LSM, IP_SET, TCP_BBR, F2FS/TMPFS opts. GOLDEN_boot (sha 82fdc60f…, lh-laptop) is the SOLE known-good; restore it to un-break the daily driver. Docker flash PAUSED until networking root-caused. Also: because attempt-5's bootloop was misdiagnosed (see KCFI note below) and attempt-6 was never boot-confirmed, the FORCE-LOAD approach itself has NEVER been shown to boot on this device — treat it as an unvalidated hypothesis, not a known-good fallback. Only the two-build gate + a real boot test will establish whether force-load works.

**Why:** past attempts bootlooped. Build #1 (wrong Debian/Linaro clang) → module_layout CRC mismatch, no drivers. Build #2 (LTO_NONE + CFI_CLANG + CFI_PERMISSIVE + forceload) → early **pre-console** malformed-CFI fault. attempt-6 (LTO_THIN + CFI + CFI_PERMISSIVE + forceload) was dd'd but boot never confirmed.

**KMI bar (measured):** stock vendor vermagic = `6.1.57-android14-11-g41519d41cdba SMP preempt mod_unload modversions aarch64`. Full required-symbol CRC bar = 3738 distinct symbol→CRC pairs across all 336 stock vendor_dlkm .ko, delivered as `ref_required_crcs.tsv` (sha256 b7de39dc…d18f4, format `0xCRC<TAB>symbol`) to `/srv/op12-kernel/vendor-ref/`.

**VERMAGIC RELEASE STRING does NOT need to match (corrected):** verified in kernel/module/version.c: `same_magic(amagic,bmagic,has_crcs)` does `amagic += strcspn(amagic," ")` when has_crcs — it SKIPS the release-string token (`6.1.57-android14-11-…`) and compares only the flags tail (`SMP preempt mod_unload modversions aarch64`). Stock vendor modules have CRCs → has_crcs=true → release prefix IGNORED. Proof: WildKernel runs as `-OP-Wild` yet loads all 521 stock vendor modules. So the ACTUAL load gates are (1) per-symbol CRCs and (2) the flags tail — NOT the release string. Pinning the release string to `-g41519d41cdba` (below) is OPTIONAL hygiene, not required; a from-source build with its own `-o-g<sha>` boots + loads vendor modules fine as long as CRCs match (0) and flags tail matches (they do by default). IMPLICATION for Docker Build B: force-load is needed ONLY for the CRC deltas, NOT for vermagic. Original claim that "vermagic string must match" was an over-correction (kept the pin anyway; harmless).

**(optional) vermagic pin details:** 0 CRC mismatch is the real gate; the loader's `same_magic()` release-token comparison is skipped when has_crcs. Stock vendor vermagic = `6.1.57-android14-11-g41519d41cdba …`. A from-source rebuild produces `6.1.57-android14-11-o-ge02429a7e0f3` (our common HEAD SHA + an `-o`), because the frozen GKI SHA `41519d41cdba` (Google's ACK android14-6.1 KMI commit) is NOT in the OnePlus tree. The CLEAN fix (better than force-load), VERIFIED WORKING: the vermagic suffix is composed in `build/kernel/kleaf/impl/stamp.bzl` `_write_localversion` as `scmversion="${scmversion_prefix}${stable_scmversion}"` where `scmversion_prefix="-$android_release-$KMI_GENERATION-$oki_infix"` (oki_infix="o" hardcoded → the `-o`) and stable_scmversion = live git `-g<sha>`. NOTE the device runs Google's certified GKI prebuilt (`-g41519d41cdba`, no `-o`), which is why a from-source build differs. FIX: edit that stamp.bzl line to `scmversion="-android14-11-g41519d41cdba"` (a .bzl edit invalidates the scmversion action + kernel relink). This produced vmlinux + all .ko vermagic EXACTLY `6.1.57-android14-11-g41519d41cdba` while CRC gate stayed 0. Do NOT use `common/.scmversion` (it APPENDS a 2nd segment → doubled string) and do NOT patch scripts/setlocalversion alone (workspace_status uses a separate git path → still doubled). stamp.bzl is the single source of truth. This makes vermagic HONESTLY agree while CRCs genuinely match → vendor modules load through NORMAL validation, no bypass. KEY REFRAME: the old force-load patch's `same_magic()→return 1` was ALSO papering over this vermagic mismatch, not just CRCs. With .scmversion pinning + 0-CRC stock build, force-load may be entirely unnecessary for a stock baseline.

**How to apply:**
- **Toolchain:** use the tree's bundled AOSP clang r487747c (clang-17), NOT Debian clang — matters for build correctness (vermagic, CFI type-ids, module_layout). BUT: the clang VERSION is IRRELEVANT to the genksyms CRCs — clang-17 vs clang-21 give byte-identical CRC results (1669 match / 754 mismatch both). genksyms checksums the expanded C type graph, not codegen. So do NOT expect "right clang" to make vendor CRCs line up.
- **Two-build gate (mandatory to interpret the CRC result):** there is NO clean stock baseline yet (the only non-Docker symvers was mis-built with BTF off + LTO_NONE → contaminated). Build BOTH via the OEM kleaf/bazel target `//msm-kernel:pineapple_gki_dist` (NOT hand-assembled fragments, NOT bare gki_defconfig — the target applies gki_defconfig + pineapple_GKI.config + oplus fragments in the exact order the shipping kernel and its 336 vendor .ko were built; bare gki omits vendor/oplus symbols → false mismatches). (A) target as-is, no Docker fragment → gate Module.symvers vs bar; (B) target + Docker fragment, same flags → gate vs bar. If A≈0 & B≈754 → Docker delta is sole cause, force-load is a Docker-only crutch. If A is ALSO large (hundreds) → local rebuild can't reproduce Google's frozen GKI KMI at all, force-load is required for ANY custom kernel here regardless of Docker. Keep force-load + MODULE_FORCE_LOAD + CFI_PERMISSIVE staged; strip only if A proves clean AND B≈0.
- **CFI/LTO — VERIFIED against the tree's own Kconfig (corrects a peer belief):** this android14-6.1 kernel uses **KCFI** (`CFI_CLANG depends on $(cc-option,-fsanitize=kcfi)`; `Makefile: CC_FLAGS_CFI := -fsanitize=kcfi`), introduced in Linux 6.1. KCFI uses NO jump tables and has **NO LTO dependency** — CFI_CLANG's Kconfig does not depend on LTO at all. So the peers' claim "CFI_CLANG requires LTO_CLANG_THIN, else pre-console jump-table fault" is the OLD (pre-6.1) CFI model and does NOT apply here; the earlier attempt-5 pre-console bootloop was almost certainly misdiagnosed (real cause unproven). PRACTICAL RULE UNCHANGED: keep the STOCK config (ThinLTO + KCFI + SCS, all on, untouched) because that is what the shipping kernel uses and boots — don't deviate from stock LTO. KCFI still does runtime indirect-call type checks, so CFI_PERMISSIVE as a force-load bring-up valve is still valid.
- **Keep `DEBUG_INFO_BTF=y`** (stock) — disabling it adds ~850 more CRC drifts.
- **Preferred sequence (per lh-laptop):** the permissive question is downstream of "do you even need force-load?" GKI already enables much cgroup/ns support, so the Docker delta may NOT break KMI. So: (1) build right-toolchain + ThinLTO + strict CFI + Docker fragment; (2) extract a real vendor .ko from vendor_dlkm/vendor_boot, read its required symbol CRCs, compare to the build's exported CRCs; (3) if CRCs match → NO force-load, NO permissive, strict CFI (cleanest); (4) only if the delta shifts imported-symbol CRCs → apply the version.c force-load patch AND add `CFI_PERMISSIVE=y` as a first-boot safety valve for the stale force-loaded vendor modules (their CFI type-ids were computed against stock layouts; a shifted fn-pointer signature would panic strict CFI at runtime). Boot that as a diagnostic image, read dmesg for CFI/module warnings, then tighten to strict.
- **Force-load patch** (only if step 3 fails): in BOTH `kernel_platform/common/kernel/module/version.c` and `.../msm-kernel/kernel/module/version.c` — make `check_version()`'s `bad_version:` path `return 1` (accept CRC mismatch), and make `same_magic()` body just `return 1`. Plus `CONFIG_MODULE_FORCE_LOAD=y`, `CONFIG_MODULE_FORCE_UNLOAD=y`.
- **Docker config delta** (add to stock defconfig; most namespaces/cgroups/netfilter already on in GKI): USER_NS, PID_NS, IPC_NS, POSIX_MQUEUE(+_SYSCTL), CGROUP_PIDS/DEVICE/PERF/NET_CLASSID, NET_CLS_CGROUP, CFS_BANDWIDTH, BRIDGE_NETFILTER, NETFILTER_FAMILY_BRIDGE, NETFILTER_XT_MATCH_ADDRTYPE/IPVS, IP_VS(+_NFCT), VXLAN, MACVLAN, IPVLAN(+_L3S), VLAN_8021Q, NET_L3_MASTER_DEV.
